# Per-participant resource identifiers

## Decision

The identity of an `Asset`, a `ContractDefinition` and a `PolicyDefinition` is the pair
`(participantContextId, id)`. Their ids are unique only within the owning participant context, not across the whole
connector:

- the SQL primary keys of `edc_asset`, `edc_contract_definitions` and `edc_policydefinitions` are composite keys on
  `participant_context_id` and the resource id, and the in-memory stores are keyed the same way;
- the store SPIs (`AssetIndex`, `ContractDefinitionStore`, `PolicyDefinitionStore`) and the service SPIs
  (`AssetService`, `ContractDefinitionService`, `PolicyDefinitionService`) resolve, update and delete these resources by
  participant context id **and** resource id. The methods that took only a resource id have been removed, there is no
  "global" lookup anymore;
- every code path that needs one of these resources passes the participant context it acts on behalf of: the Management
  API (`v4` from the runtime's `SingleParticipantContextSupplier`, `v5` from the `{participantContextId}` path segment),
  the DSP catalog, negotiation and transfer services (from the request's `ParticipantContext`), and the
  `DataFlowController` (from the `ContractAgreement`).

> This is a breaking change to the store and service SPIs and to the SQL schemas. It supersedes the statement of the
> [participant context](../2025-08-26-participant-context/README.md) decision record that "the store and service
> interface for those entities won't change".

## Rationale

The [participant context](../2025-08-26-participant-context/README.md) decision record added a `participantContextId`
to these entities, but their ids stayed globally unique and the stores kept resolving them by id alone. In a _virtual_
connector, where several participant contexts share one runtime and one database, this had two consequences:

- **existence oracle**: a participant creating a resource with an id already used by another participant received a
  `409 Conflict`, which reveals the ids in use by other tenants;
- **id squatting**: a participant could reserve ids (for example well-known asset ids) and prevent other participants
  from using them.

Moreover, several code paths resolved a resource globally by id and then _derived_ the tenant from the row they got
back, or checked ownership after the fact. This is only correct as long as ids are global. Making the participant
context part of the identity removes the whole class of problems: a participant can neither see, nor collide with, nor
modify a resource of another participant, because it never addresses one.

Resources with generated identifiers are not affected: `ContractNegotiation` and `TransferProcess` ids are always
generated by the connector, and `ContractAgreement` already combines a generated surrogate key with a unique constraint
on `(agreementId, participantContextId)`.

## Approach

### Stores

The three SQL schemas define `PRIMARY KEY (participant_context_id, <id>)`. The unique index on `policy_id` alone, that
`edc_policydefinitions` carried in addition to its primary key, is removed because it would keep enforcing global
uniqueness. The SQL stores add the `participant_context_id` predicate to every statement that addresses a single row
(find, exists, update, delete). The in-memory stores use a `(participantContextId, id)` record as map key.

The store contract tests (`AssetIndexTestBase`, `ContractDefinitionStoreTestBase`, `PolicyDefinitionStoreTestBase`)
verify that the same id can exist in two participant contexts, and that each participant context only reads, updates
and deletes its own resource.

### SPIs

| SPI                         | before                                                  | after                                                                                                                     |
|-----------------------------|---------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------|
| `AssetIndex`                | `findById(id)`, `deleteById(id)`, `resolveForAsset(id)` | `findById(participantContextId, id)`, `deleteById(participantContextId, id)`, `resolveForAsset(participantContextId, id)` |
| `ContractDefinitionStore`   | `findById(id)`, `deleteById(id)`                        | `findById(participantContextId, id)`, `deleteById(participantContextId, id)`                                              |
| `PolicyDefinitionStore`     | `findById(id)`, `delete(id)`                            | `findById(participantContextId, id)`, `delete(participantContextId, id)`                                                  |
| `AssetService`              | `findById(id)`, `delete(id)`                            | `findById(participantContextId, id)`, `delete(participantContextId, id)`                                                  |
| `ContractDefinitionService` | `findById(id)`, `delete(id)`                            | `findById(participantContextId, id)`, `delete(participantContextId, id)`                                                  |
| `PolicyDefinitionService`   | `findById(id)`, `deleteById(id)`                        | `findById(participantContextId, id)`, `deleteById(participantContextId, id)`                                              |
| `ConsumerOfferResolver`     | `resolveOffer(offerId)`                                 | `resolveOffer(participantContextId, offerId)`                                                                             |
| `DataFlowController`        | `transferTypesFor(assetId)`                             | `transferTypesFor(participantContextId, assetId)`                                                                         |

`create`, `save` and `update` keep their signatures: the participant context is taken from the entity, and the
"already exists" / "not found" semantics apply within that participant context.

The write-side check that the policies referenced by a contract definition belong to the same participant context is
dropped: policies are now always resolved within the participant context of the contract definition, so a policy of
another participant can't be referenced by accident, and a missing policy is handled where it always was, at catalog
and negotiation time.

### Migration

The schemas are applied with `CREATE TABLE IF NOT EXISTS`, so an existing database won't pick up the new primary keys
automatically. As for previous schema changes, the SQL store modules document the `ALTER TABLE` statements needed to
migrate an existing database in their `README.md`; applying them is up to the deployer.

## Follow-ups

`DataPlaneInstance` ids are user-provided as well (the `dataplaneId` of the registration message) and are still
globally unique. They will be moved to the same `(participantContextId, id)` identity together with the scoping of the
`DataPlaneSelectorService`.
